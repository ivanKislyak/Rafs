# RAFS: фоновый импорт анимации

Импортёр написан с помощью ИИ (OpenAI Codex). Команда `import_animation`
работает как отдельный CLI-процесс, без Celery/Redis и HTTP-запросов к сайту.
Она использует существующие `Movie`, Parler, HTTP-клиент, кеширование,
проверки идентичности и заполнение пустых полей из импорта фильмов/аниме.

**15 000 — целевой максимум НОВЫХ карточек за одну кампанию, а не обещанный
объём каталога.** Достигнуть его можно только при достаточном числе валидных
записей. Существующие, обогащённые, пропущенные записи, дубли и dry-run в цель
не входят. Живой массовый импорт при разработке не запускался; вместимость
источников и продолжительность кампании не измерялись.

## Отбор

- `--media-type movie|tv|both`, по умолчанию `both`. Movie: отдельные
  анимационные фильмы, включая короткометражные. TV: целые сериалы,
  мини-сериалы и подтверждённые целые web-сериалы, без отдельных сезонов/эпизодов.
- TMDB discovery требует Animation (`16`); жанр повторно проверяется в details.
  Нет обязательного жанра Family, фильтров страны, оригинального языка,
  наличия русского перевода или даты выхода до сегодняшнего дня.
- `include_adult=false`; для movie также `include_video=false`. Эти флаги
  повторно проверяются в details. Анимация для взрослой аудитории без флага
  adult допустима. `--min-votes 0` — значение по умолчанию; увеличение порога
  отсечёт часть редких, новых и малооценённых работ.
- Аниме по умолчанию включено. `--exclude-anime` исключает только точную
  метку `210024` в discovery **и** details (`keywords.keywords` для movie,
  `keywords.results` для tv). При таком режиме проверяется значение самой
  метки через TMDB. Отсутствие метки не доказывает отсутствие аниме;
  японский язык или страна не используются как замена классификации.
- Анимационность подтверждает TMDB; формат — полный bounded обход P31/P279
  Wikidata из `confirmed_format`: **64 перехода, 2048 классов**. Сохраняется
  конкретный подтверждённый прямой P31, без подмены жанром или общим film.
  Сезоны, эпизоды, конфликт movie/tv и неоднозначные типы отклоняются.
  Дополнительно запрещены классы film series (`Q24856`), media franchise
  (`Q196600`) и fictional character (`Q95074`) и их потомки. Неполная
  классификация не считается доказательством подходящего формата.

## Идентичность и сохранение данных

Movie и TV с одинаковым числовым TMDB ID — разные кандидаты. Используются
Wikidata ID из TMDB, точные TMDB/IMDb lookup и перенаправления Wikidata;
для movie — P4947, для tv — P4983, IMDb — P345. Lookup выполняется небольшими
разрешёнными пакетами, а не SPARQL-запросом на каждый объект. Перенаправление
сохраняется в квитанции как канонический QID. Перед записью действуют прежние
строгие проверки `validate_identity`, `find_existing` и `import_one`.

Без однозначного соответствия Wikidata карточка **не создаётся**:
`no_wikidata_match` отделён от `ambiguous_identity`. Несогласованные ID и
совпадение названия/года без совпадения ID дают `identity_conflict`; по названию
ничего не объединяется. Фиктивные QID и TMDB-only карточки не создаются.
Существующие аниме, фильмы и ручные карточки распознаются по этим же правилам
и не увеличивают счётчик новых. Противоречивые старые записи требуют ручного
разбора, а не автоматического объединения.

Заполняются только пустые поля и переводы, добавляются подтверждённые связи.
Существующие названия, описания, даты, типы, ID, обложки, M2M, отзывы и оценки
пользователей сохраняются. Обновляется `last_synced_at`; он сам по себе не
считается обогащением карточки. `updated` означает изменение полей Movie,
его переводов или набора связей; отдельное дозаполнение подписи связанной
сущности без изменения самой карточки может оставаться `existing`.

Реально доступные en, ru, uk, kk, es, de берутся из TMDB translations и
Wikidata labels/descriptions того же языка. Английский текст не подставляется
в русский или казахский слот. Нет машинного перевода или выдуманных дат.
Отсутствие постера, отдельных переводов или года не мешает импорту при
корректных названии, идентичности и формате. Постеры сохраняются URL в
`cover_url`; пользовательские media не скачиваются и не заменяются.
Актёры озвучивания сохраняются через P725 наряду с P161.

## Discovery и ограничения полноты

Официальный предел TMDB — 500 страниц **на запрос с заданными фильтрами**.
Команда никогда не запрашивает страницу 501. Она сначала проходит доступный
нефильтрованный список каждого источника; TV включает записи без даты первого
показа (`include_null_first_air_dates=true`). Затем идёт отдельный проход по
`primary_release_date` для movie и `first_air_date` для tv.

Датированный диапазон по умолчанию — весь представимый ISO-календарь:
`0001-01-01`–`9999-12-31`. Его можно явно сузить через `--date-from`/`--date-to`.
Границы сохраняются в кампании и не сдвигаются при возобновлении. Если раздел
содержит больше 500 страниц / 10 000 результатов, он делится пополам по датам
до достаточно малого диапазона. Включительные дочерние границы не
пересекаются: `[начало, середина]`, `[середина + 1 день, конец]`, включая
високосные годы. При переполнении одного дня скачиваются только доступные
500 страниц и фиксируется ограничение покрытия.

Источники чередуются страницами, ID внутри порции перемешиваются movie/tv.
Все ID страницы и курсор/разбиение фиксируются одной SQLite-транзакцией.
После небольшой порции сразу начинается импорт в Django; весь каталог
заранее не скачивается. Остановка на середине страницы оставляет её
необработанные ID в очереди. Дедупликация действует между разделами и проходами.

Порядок «доступные популярные, затем разделы по датам» **не является глобальной
сортировкой всего TMDB**. TMDB меняется между запросами, поэтому это также не
неизменный снимок каталога. Работы без даты, не попавшие в первые 500 страниц
нефильтрованного списка, могут остаться необнаруженными. Датированный проход
этого не исправляет. Ограниченный тест на 40 кандидатах не оценивает полную
ёмкость. Ошибки разметки, отсутствие Wikidata и недостаточная классификация
дополнительно ограничивают результат. Условия ради числа не ослабляются.

## Состояние и атомарная квитанция

Нужны PostgreSQL и применённая миграция
`movies/0047_animation_import_receipt.py`. Единственная новая служебная модель
`AnimationImportReceipt` не является новой моделью произведения. В неё
записываются UUID кампании, составной TMDB ID, канонический QID, Movie,
результат и состояние индексации. Квитанция и Movie/переводы/M2M сохраняются
**в одной транзакции Django**, после получения всех сетевых данных.

SQLite и PostgreSQL не имеют общей транзакции. Поэтому после сбоя между
commit Django и обновлением SQLite следующий запуск восстанавливает результаты
по квитанциям. Счётчик `created_in_campaign` берётся из квитанций, а не из
предположения, что ранее найденная карточка была создана сейчас. Повторное
сохранение и двойной подсчёт исключаются. Если карточку позже удалили вручную,
квитанция сохраняется (связь SET_NULL); число исторически созданных карточек
не уменьшается, автоматическое повторное создание этого кандидата не делается.

По умолчанию используется **только** `.rafs_import/animation/`:

- `state.sqlite3`: версия importer/schema, отпечаток целевой БД без секретов,
  фильтры, языки, источники, диапазоны, курсоры, составная очередь, API cache;
- `summary.json`: периодическая сводка (примерно раз в минуту между порциями)
  и финальный статус; при работающем процессе возможен статус `running`;
- `import_report.csv`: потоковая выгрузка всех кандидатов при завершении,
  источник/ID, результат, QID, Movie pk, причина, попытки, исходные раздел/страница
  и отдельные результаты последнего dry-run;
- `discovery_report.csv`: разделы, границы, страницы, разбиения и флаг `limited`;
- `run.lock`: файловая блокировка. Папку не нужно коммитить или удалять при resume.

Чужие состояния аниме/фильмов и несовместимые БД/наборы фильтров отклоняются
до записи в них. Для другой выборки используй отдельный `--state-dir`.
Target и предохранитель не входят в отпечаток выборки: их можно увеличить
без удаления прогресса. `--target-new` допускает 1–15000. `--max-candidates N`
ограничивает проверки **в текущем запуске**, включая пропуски; 0 — без
предохранителя. Тот же предохранитель при следующем запуске разрешает ещё N
кандидатов. Предварительная проверка порции до 20 записей может дать больше
`examined`, чем реально завершённых объектов при достижении цели посреди порции.

Храни Django БД и папку состояния как согласованную кампанию. Не удаляй
квитанции для «обнуления» цели. Не переиспользуй старое состояние с восстановленной
несогласованной копией БД; отпечаток подключения не обнаруживает подмену БД
другим содержимым на том же адресе. Для отдельного тестового клона используй
свой state-dir. Восстановление более старой SQLite-копии с прежним UUID при
сохранённых квитанциях Django восстанавливает завершённые кандидаты.

Файловая и общая PostgreSQL advisory lock совпадают по механизму со старыми
импортёрами. Они **не ставят процесс в очередь**: конкурирующий запуск сразу
завершается ошибкой. Разные state-dir не позволяют двум импортёрам одновременно
писать в одну PostgreSQL. Ручные действия/внешние писатели, не использующие эти
блокировки, не превращаются ими в очередь задач.

## Режим пробы и эксплуатация на Ubuntu

Из `~/apps/Rafs`, активировав существующую `.venv`:

```bash
cd ~/apps/Rafs
source .venv/bin/activate
python manage.py check
python manage.py migrate
```

Нужен `TMDB_READ_TOKEN` либо `TMDB_API_KEY` в существующем `.env`. Не передавай
секрет аргументом CLI. Код не печатает и не сохраняет его в CSV, cache или
конфигурации. На разработке миграции и проверки запускались в отдельной БД.

Сначала короткая проба **без изменений Django**, в отдельной папке:

```bash
python -u manage.py import_animation --media-type both --target-new 15000 --min-votes 0 --max-candidates 40 --dry-run --state-dir .rafs_import/animation-probe
```

Dry-run пишет только локальные discovery/cache/report, не меняет Django,
квитанции, реальный target, terminal status очереди и поисковый индекс.
`would_create` означает предложение новой карточки; `would_existing` —
найденную существующую; `would_duplicate` — повтор QID в этой пробе.
Это не созданные строки и не прогноз результата полной кампании.
Проверки отдельных кандидатов не симулируют все взаимные конфликты будущих
вставок, поэтому apply может дополнительно остановить совпадение названия/года.

При желании первый настоящий запуск тоже можно ограничить 40 проверками,
но использовать **основное** состояние, чтобы созданные карточки уже считались
частью её цели 15000:

```bash
python -u manage.py import_animation --media-type both --target-new 15000 --min-votes 0 --max-candidates 40
```

После проверки отчёта основная команда / resume:

```bash
python -u manage.py import_animation --media-type both --target-new 15000 --min-votes 0
```

Для фонового запуска (папка логов вне состояния, exit code не теряется в tee):

```bash
tmux new-session -s rafs-animation
cd ~/apps/Rafs
source .venv/bin/activate
mkdir -p logs
set -o pipefail
python -u manage.py import_animation --media-type both --target-new 15000 --min-votes 0 2>&1 | tee -a logs/import-animation.log
animation_codes=("${PIPESTATUS[@]}")
printf 'Python exit code: %s; tee exit code: %s\n' "${animation_codes[0]}" "${animation_codes[1]}"
```

Массив `PIPESTATUS` сохраняет точный код Python отдельно от кода tee; `pipefail`
также делает pipeline неуспешным при ошибке любого из них.
Отсоединение: **Ctrl+B, затем D**.
Возврат: `tmux attach -t rafs-animation`. tmux переживает закрытие SSH,
но не reboot: после перезагрузки запусти основную команду заново в tmux.
Сохранённая кампания продолжится.

Остановка: Ctrl+C в терминале процесса либо SIGTERM его Python PID. Текущий
объект завершается/откатывается; уже committed квитанции и карточки остаются.
Коды остановки: 130 для SIGINT, 143 для SIGTERM. SIGKILL не может выполнить
cleanup, но ОС освобождает lock, а следующий запуск восстанавливается по
атомарным квитанциям. Незавершённая индексация тоже продолжится при resume.

Контроль из другого терминала:

```bash
cd ~/apps/Rafs
tail -f logs/import-animation.log
cat .rafs_import/animation/summary.json
head -n 5 .rafs_import/animation/import_report.csv
head -n 5 .rafs_import/animation/discovery_report.csv
tmux list-sessions
```

CSV отражает последний завершившийся запуск; во время работы актуальны SQLite,
лог и периодическая JSON-сводка. Выгрузка потоковая, весь каталог в память не
загружается, CSV не переписывается после каждого отдельного объекта.

Финальные статусы: `target_reached`, `source_exhausted`,
`candidate_budget_reached`, `interrupted`, `failed`. Исчерпание предохранителя
не означает исчерпание источника. `source_exhausted` означает завершение всех
сохранённых доступных проходов/разделов, а не доказательство полноты TMDB:
проверь `coverage_limited_partitions` и ограничения записей без даты выше.

`summary.json` разделяет текущий `run` и `campaign_state`, содержит реальное
`created_in_campaign`, `shortfall`, pending index и пропуски по причинам.
При недоборе смотри особенно `campaign_state.skips_by_reason.no_wikidata_match`:
это количество кандидатов, заблокированных отсутствием Wikidata-соответствия.
Неоднозначность, конфликты, неподходящий формат и жанр учитываются отдельно.
`failed_runs` — число неуспешных запусков, а не окончательно потерянных объектов.

Повторная проверка пропущенных после ручного разбора / обновления источников:

```bash
python -u manage.py import_animation --media-type both --target-new 15000 --min-votes 0 --retry-skipped --refresh-cache
```

Это возвращает пропущенные ID в очередь, не меняя созданные квитанции. Если
цель уже достигнута, новых проверок не будет. `--refresh-cache` очищает только
API cache этой кампании; самостоятельно не сбрасывает terminal status,
discovery/cursors или квитанции. Паузы можно увеличить через `--tmdb-delay`,
`--wikidata-delay`, `--sparql-delay`; минимумы 0.6/1/5 секунд сохранены.
HTTP timeout `(15,70)`, Retry-After, ограниченные 429/5xx/network retry,
`maxlag=5` и бюджет `--maxlag-wait 1800` переиспользуются. Временная ошибка
API останавливает запуск с прогрессом, а не становится `no_wikidata_match`.

## Поиск

Автоматических signals в текущем проекте нет; общие `index_new_*` сами по себе
не обновляют готовые документы. Здесь после ограниченной порции обновляются
только затронутые Movie через тот же построитель, в атомарной транзакции.
Остальные документы сохраняются. Receipt.indexed позволяет завершить этот
шаг после сбоя даже при уже достигнутом target. Dry-run его не выполняет.

Векторы Movie учитывают все шесть языков: существующие словари en/ru/es/de и
`simple` для uk/kk. Последние доступны как буквальные токены через существующий
поиск; полноценная украинская/казахская морфология не заявляется. Уже
непустые документы других фильмов не обновляются этим импортом.

Для полного обновления связанных Person/Studio, старых карточек или после
ручных правок можно **отдельно после импорта** выполнить существующую команду
без аргументов:

```bash
python manage.py rebuild_search_index
```

Она атомарно пересобирает все пять типов документов. Это необязательный
завершающий шаг для всего индекса, не действие перед каждым объектом и не
часть dry-run. На рабочей БД при разработке он не запускался.

## Проверки и первоисточники

Тесты `movies.test_import_animation`, `movies.test_import_anime`,
`movies.test_search_index` и `movies.tests.SearchResultsAPITests` используют
mocked HTTP и отдельную PostgreSQL test-БД. Они проверяют составные ID,
конкретные форматы, фильтры, сохранение ручных данных, переводы, голоса/отзывы,
квитанцию между двумя хранилищами, SIGINT/SIGTERM, блокировки, target/budget,
разбиение дат, dry-run, retry и доступность новых названий в поиске.
Тесты не оценивают живую ёмкость TMDB/Wikidata; production не проверялся.

- [TMDB Discover movie](https://developer.themoviedb.org/reference/discover-movie)
- [TMDB Discover TV](https://developer.themoviedb.org/reference/discover-tv)
- [TMDB errors: код 22, максимум 500 страниц](https://developer.themoviedb.org/docs/errors)
- [Wikidata: TMDB movie ID P4947](https://www.wikidata.org/wiki/Property:P4947)
- [Wikidata: TMDB TV ID P4983](https://www.wikidata.org/wiki/Property:P4983)
- [Wikidata: film series](https://www.wikidata.org/wiki/Q24856)
- [Wikidata: media franchise](https://www.wikidata.org/wiki/Q196600)
- [Wikidata: fictional character](https://www.wikidata.org/wiki/Q95074)

Прежние требования атрибуции TMDB из README основного импортёра сохраняются.
